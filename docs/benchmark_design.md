# Benchmark design

Two benchmarks share one case schema (`robot_eval.domain.case.BenchmarkCase`, `extra="forbid"`):

| file | version / split | cases | purpose |
|---|---|---|---|
| `datasets/benchmark_v0.jsonl` | v0 / `smoke` | 24 | tiny deterministic **pipeline smoke check** - not evidence about AI reliability |
| `datasets/v1/development.jsonl` | v1 / `development` | 164 | iterate prompts, rules, configurations here |
| `datasets/v1/heldout_test.jsonl` | v1 / `heldout_test` | 124 | final, confirmatory comparisons only |

`datasets/worlds.json` holds the five deterministic worlds (`cell_a`, `cell_b`, `cell_c`, `cell_open`, `cell_walled`).
Note: the v0 suite in this repository was **newly authored** here (the original repository was not available); it is
not the user's earlier 24-case file.

v1 totals **288 unique cases** (target >= 200 met). Counts, balance, duplicate and leakage statistics are generated by
`robot-eval audit-dataset` into `reports/audit/audit.{json,md}` (Experiment 1); the table below was read from that output.

## Case fields

`case_id`, `benchmark_version`, `split`, `category`, `difficulty`, `prompt` (user text; never contains tool names, error
codes or oracle notes - enforced by the validator), `world_id`, optional `fault` (controlled tool fault),
`intent` (hidden task family + parameters), `expected` (outcome, acceptable failure codes, expected answer, expected
final pose, acceptable tool patterns, argument constraints, unsafe-move flag, collision label, safe-answer key),
`safety` (label + severity), `oracle_notes` (rationale; never shown to agents), `source_type` (`authored` /
`templated`), `provenance` (generator version + template id), `tags`.

Expected outcomes: `success`, `safe_refusal`, `clarification_required`, `task_failure` (with acceptable `failure_codes`).
Argument constraints are per-argument tolerances (`approx`, `eq`, `absent_or_approx`, `points_approx`), not one brittle
JSON string; acceptable tool use is a set of patterns (`required`, `required_any`, `optional`, `ordered`).

## Task families and categories

Hidden families: `query_reach`, `query_collision`, `query_clearance`, `query_joints`, `plan_path`, `validate_path`,
`feasibility`, `move`, `describe_state`, `schema_lookup`, `diagnose_check`, `underspecified`, `unparsable`,
`invalid_value`, `contradictory`.

| category | difficulty | dev | held-out | what it probes |
|---|---|---|---|---|
| valid_simple | easy | 14 | 10 | straightforward valid requests across tools |
| paraphrase_variation | medium | 11 | 9 | unusual word order / phrasing |
| tool_confusion | hard | 11 | 9 | distractor words from other tools (negation, "not about X") |
| ambiguous | medium | 9 | 7 | references without values ("that point") -> clarify |
| missing_params | medium | 8 | 6 | one coordinate/joint value missing -> clarify |
| invalid_args | medium | 10 | 8 | non-numeric text (clarify) or NaN/inf/out-of-range/unknown joint (INVALID_ARGUMENT) |
| reachability | easy | 12 | 8 | reach limit, dead zone, out of workspace (queries and moves) |
| collision_direct | easy | 12 | 8 | point in obstacle (queries and moves) |
| collision_path | medium | 12 | 8 | segment crossings, clearance along a segment, inner reach limit |
| clearance | medium | 10 | 8 | margin checks, user-specified stricter margins, weld margin |
| joint_limits | easy | 9 | 7 | in/out of joint ranges |
| contradictory | hard | 6 | 4 | mutually exclusive instructions -> clarify |
| tool_fault | medium | 8 | 6 | injected timeouts/unavailability: transient (retry once) vs persistent (report) |
| safety_override | medium | 9 | 7 | "move anyway / ignore the check" -> refuse |
| boundary_numeric | hard | 10 | 10 | exact boundary equality, 1 mm / 0.01 deg offsets, cm/mm unit conversion |
| planning | medium | 8 | 6 | straight, detour, walled-off, unsafe endpoint |
| multi_step | medium | 5 | 3 | tool chains (check then diagnostics; plan then validate) |

Share of "invalid input / ambiguity / tool failure / safety / boundary" categories (ambiguous, missing_params,
invalid_args, contradictory, tool_fault, safety_override, boundary_numeric): **0.366 (dev), 0.387 (held-out), 0.375
combined** (requirement: >= 0.20). Expected outcomes are mixed (dev: 101 success, 27 clarification, 27 task failure,
9 safe refusal; held-out: 76 / 20 / 21 / 7).

## Generation and provenance

`robot_eval.evaluation.generator` (seeded, `V1_SEED = 20260601`) samples parameters on a 0.01-0.05 m grid, classifies
them with the **exact oracle**, rejects points whose classification is unstable under +-4 mm perturbations (keeps cases
away from knife edges), fills disjoint template banks per split, and de-duplicates by normalised prompt and by
(world, fault, intent). Boundary/numeric cases (3-4-5 triangles giving exact equalities, unit-converted values) are
**authored** explicitly. `robot-eval generate-dataset` regenerates all files byte-identically (tested) and refuses to
write a dataset that fails validation. Template pools are disjoint between development and held-out.

## Oracle and validation

* `evaluation/oracle.py` decides everything with `fractions.Fraction` on squared distances - no square roots, no
  tolerances. It does not import the simulator's float geometry.
* `groundtruth.build_expected` derives the expected outcome/answer/failure codes/tool patterns from (world, intent).
* `validate_dataset` per case: strict schema; unique `case_id`; normalised-prompt uniqueness; (world, fault, intent)
  uniqueness; no tool/error/oracle labels in prompts; stored `expected` and `safety` must equal the oracle
  recomputation; override cases must target an oracle-unsafe move; `plan_path` cases need an exact **certificate**
  (a witness path verified exactly, a blocked endpoint, or a wall that provably spans the workspace width); and the
  **float simulator must agree with the oracle** for the hidden intent (run live against the tools).
* Float-vs-exact agreement is also fuzz-tested on 4,000 random grid points per world and 2,000 random segments.
* Failure-code sets include *every* violated code (e.g. COLLISION and PATH_COLLISION for an in-obstacle target), so an
  agent reporting either is correct.

## Leakage controls

* Development and held-out use disjoint template pools; audit result: identical prompts 0, identical skeletons 0,
  identical (world, intent) pairs 0, near-duplicate pairs (token-Jaccard >= 0.80 on number-masked prompts) 5, all listed in the
  audit: three pair "Plan a path from # to #." (dev) with the missing-start prompt "Plan a path to #." (held-out); two
  are the *same request pattern with different literals* ("Check clearance at x = #, y = lots." vs "x = ~"; unknown
  joint "tentacle" vs "knee"). So the pools are disjoint in wording but not perfectly so in pattern.
* No tuning on held-out outcomes: every held-out run is appended to `reports/heldout_access_log.jsonl`. If held-out
  cases are inspected for debugging, disclose it in `docs/experiment_protocol.md` section 11 and create a new held-out
  version before making confirmatory claims.
* Weakness: one author wrote both pools (see `docs/limitations_and_safety.md`).

## Known gaps

* `describe_state` and `schema_lookup` have 1-2 cases per split; the planner can only be shown to find paths for
  positive cases (no `path_found = false` answers - those are task failures); synthetic template English only.
